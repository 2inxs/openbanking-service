# Миграции PostgreSQL

Нужен PostgreSQL 15+. Используем `golang-migrate` v4.20.1; миграции запускаются отдельно от API. Пул соединений и локальное окружение относятся к #7.

```sh
go install -tags pgx5 github.com/golang-migrate/migrate/v4/cmd/migrate@v4.20.1
```

Если команда `migrate` не найдена, добавьте каталог `bin` из `go env GOPATH` в `PATH`.

## Применение

Создайте пустую БД. Имя `openBanking` в примере совпадает с регистром имени в pgAdmin; PostgreSQL не устанавливается вместе с этими миграциями.

Пароль сохраните локально в файле PostgreSQL: `%APPDATA%\postgresql\pgpass.conf` на Windows или `~/.pgpass` на Linux/macOS. Формат строки:

```text
localhost:5432:openBanking:postgres:ВАШ_ПАРОЛЬ
```

На Linux/macOS файл должен иметь права `0600`. В пароле внутри этого файла символы `:` и `\` экранируются обратным слешем. Парольный файл не добавляется в Git. `sslmode=disable` в примерах предназначен для локальной БД.

Из корня репозитория, PowerShell:

```powershell
$env:MIGRATION_DATABASE_URL = 'pgx5://postgres@localhost:5432/openBanking?sslmode=disable'
migrate -path migrations -database "$env:MIGRATION_DATABASE_URL" up
migrate -path migrations -database "$env:MIGRATION_DATABASE_URL" version
```

Linux/macOS:

```sh
export MIGRATION_DATABASE_URL='pgx5://postgres@localhost:5432/openBanking?sslmode=disable'
migrate -path migrations -database "$MIGRATION_DATABASE_URL" up
migrate -path migrations -database "$MIGRATION_DATABASE_URL" version
```

После применения версия — `2`, без `dirty`. Повторный `up` сообщает `no change`, данные не дублируются. Утилита ведёт таблицу `schema_migrations` и блокирует одновременное применение миграций. `.env.example` — образец, команды не загружают его автоматически.

Если таблицы уже созданы вручную через pgAdmin, не запускайте поверх них начальную миграцию и не ставьте `force 2` без проверки. Для такой БД нужно отдельно сверить столбцы, ограничения, индексы, функции и начальные данные. Самый простой запуск с нуля — другая пустая БД; существующие таблицы удалять для этого не нужно.

## Состав

- `000001_initial_schema`: 13 таблиц по схеме v2 от 2026-11-22, ограничения, индексы и триггеры.
- `000002_demo_data`: RUB/USD/EUR/JPY, четыре общие категории, банк `mockbank`, демопользователь.

Демопользователь: `00000000-0000-4000-8000-000000000100`, email `demo@openbanking.invalid`. Значение `password_hash = '!'` — маркер отключённого парольного входа, не общий пароль. В демонстрационном API пользователь выбирается сервером через будущий параметр `DEMO_USER_ID`; миграция сама не добавляет регистрацию или аутентификацию.

Коды валют — начальный демонстрационный набор, не полный ISO 4217. При подключении банка с другими валютами справочник надо дополнить отдельной миграцией. Данные счетов, операций, подключений и токенов миграции не создают.

## Правила хранения

- `amount` и остаток — `numeric(20,4)`, курс к RUB — `numeric(24,10)`. Расход отрицательный, приход положительный. Неизвестный остаток — `NULL` вместе с `balance_as_of`.
- `accounts.bank_connection_id` может отсутствовать у счёта из выписки. Составной FK проверяет владельца и банк при заполненном подключении. Номер счёта может отсутствовать, если есть внешний ID.
- Внешний ID счёта уникален в банке, внешний ID операции — только в рамках локального счёта. `NULL` допускается до сопоставления выписки и API. MVP не моделирует совместное владение одним внешним счётом разными пользователями.
- `UNIQUE(account_id,deduplication_key)` не заменяет алгоритм сопоставления: два разных платежа с одинаковыми суммой и временем должны иметь разные ключи. Внешний ID и ключ нельзя переписывать при повторном синке; первое заполнение пустого внешнего ID разрешено.
- У операции должна быть хотя бы одна из банковских дат `booked_at`/`value_at`; для `booked` обязательна `booked_at`. `occurred_at` — неизменяемое время для ленты, не время синхронизации. Операции без обеих банковских дат текущая схема не принимает.
- Неупавший импорт уникален по счёту и SHA-256 файла. После `failed` разрешена новая попытка. Успех и операции фиксируются одной транзакцией.
- На подключение допускается одно `authorised`-согласие. Старое закрывается до активации нового в той же транзакции; срок доступа и фактический ответ банка проверяет usecase.
- Обновления подключения, токенов и операции выполняются с `WHERE version = ожидаемая_версия` (`row_version` у операции). Триггер увеличивает версию; ноль изменённых строк означает конфликт. Одного столбца версии без этого протокола недостаточно.
- Автокатегоризация обновляет категорию только при `is_category_manual = false`. Это правило usecase; БД не определяет, кто именно прислал UPDATE.
- История операций не удаляется каскадно. Технические логи идут в stdout; `audit_logs` хранит бизнес-аудит, без FK на пользователя, с `details jsonb` и PK `(logged_at,id)`. Партиции пока не создаются.
- Пароли и токены не логируются. Шифрованные токены и PKCE verifier — `bytea`, ключи шифрования находятся вне БД. OAuth-попытки требуют периодической очистки.

## Совместимость с Go-моделями

В БД статусы и источник теперь `text + CHECK`, без таблиц статусов. В существующих доменных моделях ещё числовые константы. Репозитории должны явно преобразовывать их, а не записывать число в строковый столбец:

| Тип Go | Значения БД |
|---|---|
| `ConnectionStatusID` | `1 → active`, `2 → error`, `3 → disconnected`, `4 → pending` |
| `AccountTypeID` | `1 → current`, `2 → credit_card`, `3 → savings`, `4 → deposit`, `5 → unknown` |
| `AccountStatusID` | `1 → active`, `2 → closed`, `3 → unknown` |
| `TransactionStatusID` | `1 → pending`, `2 → booked`, `3 → rejected` |
| `TransactionSourceID` | `1 → open_banking`, `2 → statement` |

Исходный банковский статус хранится отдельно в `raw_bank_status`. Его нормализует банковский адаптер; нового значения банка не должно быть во внешнем ключе справочника. `CustomerID` текущей Go-модели соответствует внешнему `bank_connections.external_customer_id`. Текущая Go-валидация ещё требует номер счёта — поддержку счёта только с внешним ID надо добавить вместе с репозиторием в #8.

## Проверка и откат

В CI используется отдельный PostgreSQL 17. Проверяются `up`, повторный `up`, ограничения, `down`, отсутствие оставшихся таблиц/функций и повторный `up`. SQL-проверки из `tests/migrations/integrity.sql` целиком откатывают свои тестовые записи.

Ручная проверка ограничений через `psql`:

```sh
psql -h localhost -p 5432 -U postgres -d openBanking -X -v ON_ERROR_STOP=1 -f tests/migrations/integrity.sql
```

Откат удаляет схему и её данные. Его проверяют только в отдельной тестовой БД; не выполняйте его на рабочей `openBanking`. Для одной версии команда — `migrate ... down 1`. Для полного отката тестовой БД — `migrate ... down -all`. Без `CASCADE`: зависимые пользовательские данные препятствуют откату начальных данных.

Применённые миграции после merge не редактируем. Последующие изменения добавляем новой парой `up.sql`/`down.sql`. При `dirty` сначала выясняем причину и состояние БД; `force` не исправляет структуру.
