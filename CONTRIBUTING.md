# Командная разработка

Работаем небольшими Pull Request в `main`. Перед началом назначьте себя исполнителем задачи на доске и переведите её в In progress.

## Ветки и объём PR

- Обновите локальный `main` перед созданием ветки.
- Название ветки: `feat/12-transactions-list`, `fix/12-pagination` или `chore/3-ci`.
- Один PR — одна небольшая задача или несколько тесно связанных изменений.
- Не смешивайте реализацию задачи с несвязанным переименованием и форматированием.
- Общие модели, миграции и HTTP-контракты согласовывайте с разработчиками соседних задач.

## Локальные проверки

Используйте версию Go из `go.mod` или совместимую более новую версию.

```sh
go fmt ./...
go build ./...
go vet ./...
go test ./...
```

CI дополнительно запускает тесты с детектором гонок. При установленном C-компиляторе их можно повторить локально:

```sh
go test -race -count=1 -timeout=2m ./...
```

Неправильное форматирование должно исправляться в ветке автора. CI его обнаруживает, но не коммитит исправления.

## Описание и ревью

1. Заполните шаблон PR: проблема, результат и способ проверки.
2. Добавьте `Closes #12`, если PR полностью решает задачу №12. Для частичного решения используйте `Refs #12`.
3. Переведите карточку в Review и запросите проверку другого участника.
4. Исправьте замечания и дождитесь успешного CI.
5. После одобрения выполните squash merge в `main`; сохраните `Closes #N` в описании PR.
6. Проверьте закрытие задачи и переведите карточку на доске в Done.

Автор не одобряет собственный PR. Если меняется способ запуска или конфигурация, обновите README и `.env.example`.

## Что CI проверяет

На каждом PR в `main`, его обновлении и push в `main` запускаются форматирование, сборка, `go vet` и тесты. Для этих проверок не нужны банковские токены, внешние API и PostgreSQL.

Добавляя интеграционные тесты с БД, явно отделяйте их от текущих проверок без внешних сервисов и настраивайте необходимое окружение.

## Настройки main

Защита `main` требует Pull Request, одно одобрение, успешную проверку `Go checks` и актуальность ветки относительно `main`. Настройки защиты действуют отдельно от workflow; пользователи с правом обхода защиты могут обойти эти требования.

После изменения `main` workflow `Update PR branches` подливает его в открытые ветки PR этого репозитория, включая черновики. Новый или обновлённый PR также проверяется на актуальность. Затем обычный CI проверяет результат объединения. Автоматического слияния PR в `main` нет.

При конфликте ветка остаётся без изменений. Исправьте конфликт вручную и отправьте коммит: автоматическая проверка повторится. Если автор изменил ветку во время обновления, автоматика пропускает запись, сохраняя изменения автора. PR из форков не обновляются.

Для обновления используется отдельный SSH deploy key с правом записи только в этот репозиторий. Его закрытая часть хранится в Actions secret `PR_BRANCH_SYNC_KEY`, открытая — в Settings → Deploy keys. Личный токен в автоматизации не используется. Для отключения удалите deploy key и secret либо отключите workflow. Код обновления всегда запускается из `main`; файлы PR с ключом записи не исполняются.

## Архитектурные границы

- `domain` не зависит от HTTP и PostgreSQL.
- `usecase` описывает сценарии и необходимые ему интерфейсы.
- `infrastructure` реализует работу с БД, файлами и внешними API.
- `delivery/http` преобразует HTTP-запросы и вызывает сценарии.
- `app` соединяет компоненты и управляет их запуском и остановкой.

Unit-тесты располагаются рядом с кодом. В `tests` размещаем общие интеграционные и сквозные сценарии. Пароли, токены и реальные выписки в репозиторий не добавляем.
