# Алгоритм дедупликации операций из Open Banking API и выписок

## 1. Назначение и инвариант хранения

В таблице `transactions` действует составной уникальный индекс:

```sql
CREATE UNIQUE INDEX "transactions_dedup_uq" ON "transactions" ("account_id", "deduplication_key");
```

Поле `deduplication_key` (`varchar(64)`, SHA-256 в нижнем регистре) вычисляется единой чистой функцией `domain.ComputeTransactionDeduplicationKey` до записи в БД и используется одинаково в сценариях синхронизации банковского API (`internal/usecase/banksync`) и потокового импорта выписок (`internal/infrastructure/statement`, `internal/infrastructure/postgres`).

## 2. Приоритет признаков и формулы ключа

Для защиты от коллизий разделителя `|` при произвольных идентификаторах банка все строковые компоненты кодируются с явной длиной (`<tag>:<len>:<value>`).

### Приоритет 1: Стабильный внешний идентификатор (`external_id`)
Если у операции присутствует непустой `external_id` (после `TrimSpace`, длиной до 255 символов, без управляющих символов), ключ вычисляется исключительно по паре `(account_id, external_id)` независимо от источника (`open_banking` или `statement`):

```text
deduplication_key = sha256(
  "v1|acc:" + len(account_id) + ":" + account_id +
  "|ext:" + len(ext_id) + ":" + ext_id
)
```

**Следствия и порядок загрузки (`API <-> выписка`):**
1. **Повторная синхронизация API:** повторный запрос тех же операций возвращает тот же `external_id` -> `deduplication_key` совпадает, дубликаты не создаются (`ON CONFLICT (account_id, deduplication_key) DO NOTHING`).
2. **Пересекающиеся выписки с `external_id`:** если две выписки за пересекающиеся периоды (например, `01–15 ноября` и `10–25 ноября`) содержат `external_id`, общие операции имеют одинаковый ключ и не создаются повторно.
3. **Прямой порядок (`API -> выписка`):** если операция уже загружена из Open Banking API, последующий импорт выписки с тем же `external_id` формирует идентичный `deduplication_key` и пропускает строку без перезаписи метаданных API (`source = 'open_banking'`).
4. **Обратный порядок (`выписка -> API`):** если операция сначала импортирована из выписки (`source = 'statement'`, `status = 'booked'`), а затем получена через синхронизацию API (`#20`) с тем же `external_id`, совпадение `(account_id, deduplication_key)` предотвращает создание дубликата и не откатывает подтверждённый статус `booked`.

### Приоритет 2: Операции выписки без `external_id`
Одинаковые сумма и дата сами по себе **не считаются** дубликатом: пользователь может совершить два реальных платежа на одинаковую сумму в один день (например, две поездки или две покупки в одном магазине).

Если в строке выписки `external_id` отсутствует, операция **не удаляется молча**, а получает позиционный ключ в рамках конкретного акта импорта:

```text
deduplication_key = sha256(
  "v1|acc:" + len(account_id) + ":" + account_id +
  "|imp:" + len(statement_import_id) + ":" + statement_import_id +
  "|line:" + row_number +
  "|at:" + len(booked_at_utc_rfc3339nano) + ":" + booked_at_utc_rfc3339nano +
  "|amt:" + len(amount) + ":" + amount +
  "|cur:" + len(currency) + ":" + currency
)
```

### Приоритет 3: Недостаточно данных для надёжного сопоставления
Если операция пришла из `open_banking` без `external_id` (нарушение контракта банка) либо строка выписки не имеет валидного `statement_import_id` или положительного номера строки, функция возвращает `domain.ErrInsufficientDeduplicationData` и не выполняет скрытое слияние.

## 3. Матрица сценариев и ограничения MVP

| Сценарий | Поведение в MVP |
| :--- | :--- |
| Повторная синхронизация API | Операции с тем же `external_id` пропускаются по `(account_id, deduplication_key)`. |
| Пересекающиеся выписки (с `external_id`) | Пересекающиеся строки пропускаются; новые строки добавляются атомарно. |
| Операция из API, затем из выписки (одинаковый `external_id`) | Ключи совпадают; дубль из выписки не создаётся, исходная запись из API сохраняется. |
| Операция из выписки, затем из API (одинаковый `external_id`) | Ключи совпадают; дубль при синхронизации API не создаётся, статус `booked` сохраняется. |
| Два реальных одинаковых платежа в один день без `external_id` в одной выписке | Сохраняются обе операции (разные `row_number`). |
| **Ограничение MVP:** одна и та же операция без `external_id` в двух *разных* файлах выписок или в API (без ID) и выписке (без ID) | Без `external_id` или уникального номера документа невозможно отличить дубль между разными выгрузками от двух реальных одинаковых платежей без риска потери данных. Повторная загрузка *того же самого файла* отслеживается по `file_sha256` в `statement_imports`, а автоматическое нечёткое слияние по сумме/описанию в MVP намеренно не выполняется. |
