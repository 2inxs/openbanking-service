# Граница сохранения

Операции PostgreSQL находятся в `TransactionRepository`, интерфейс — в `usecase/transaction`.
`Create` не строит ключ дедупликации сам: вызывающий сценарий передаёт устойчивую идентичность операции.
Ожидаемые дубли возвращают `transaction.ErrConflict`; ошибки ограничений данных не выдаются за успешный пропуск.
`List` ограничен владельцем и счётом, использует период `[from,to)` по `occurred_at` и порядок `(occurred_at DESC,id DESC)`.
Пустой список возвращается только для доступного счёта; отсутствующий и чужой счёт дают `transaction.ErrNotFound`.
Курсор репозитория — структурированная пара времени и UUID. Проверка/подпись HTTP-курсора остаётся delivery/usecase.

Интерфейс транзакции объявлен у каждого потребителя:

- `banksync.TransactionRunner` выдаёт `banksync.Repositories`: счета, подключения и операции. Сценарий #18
  остаётся в `usecase/banksync`; ему не нужен импорт пакета, который сам зависит от `banksync`.
- `statement.TransactionRunner` выдаёт `statement.Repositories`: операции и записи импорта.
  Будущий сценарий сохранения через этот интерфейс остаётся в `usecase/statement`.

При подключении сценариев в `app` передаются `postgres.NewBankSyncUnitOfWork(pool)` и
`postgres.NewStatementUnitOfWork(pool)`. В этом PR HTTP-сценарии к ним ещё не подключены.
Оба адаптера вызывают общую реализацию открытия, commit и rollback. Каждый callback получает
репозитории на одной `pgx.Tx`; SQL-типы не попадают в usecase, транзакция не прячется в контексте.

В callback разрешены действия сохранения. Данные банка и файл читаются и валидируются ДО вызова `Within`.
Репозитории из callback нельзя сохранять для последующего использования или передавать другим горутинам.
Ошибка callback откатывает изменения, успешное завершение фиксирует их вместе.

Запись импорта создаётся `pending`, затем переводится в `processing` и `completed` либо `failed`.
Терминальные состояния не открываются повторно; повторная попытка после `failed` — новая запись.
Переход требует ожидаемый статус: устаревший писатель получает `statement.ErrImportConflict`.
Счётчики и безопасное сообщение ошибки фиксируются вместе с конечным статусом.
Допустимые переходы определены в `statement.CanTransition`, проверки состояния и счётчиков —
в `ImportRecord.Validate` и `ValidateForCreate`. PostgreSQL вызывает эти правила и применяет
изменения с проверкой владельца и ожидаемого статуса в `WHERE`.

Если сама попытка была внутри откатившейся транзакции, её записи больше нет. После возврата ошибки
создайте отдельную запись `failed` через `ImportRecordRepository` вне откатившейся транзакции.
Не сохраняйте исходные ответы банка, токены или персональные данные в error_message.

Существующий StatementImportRepository.ImportStream сохраняет свой специализированный путь CopyFrom,
но SQL-транзакция теперь начинается только после получения и валидации всех входных чанков и SHA-256.
Внутри транзакции нет ожидания загрузки исходного файла. Для MVP подготовленные строки удерживаются
в памяти: штатный парсер ограничивает файл 10 МБ, репозиторий дополнительно ограничивает 100 000 операций.
Это осознанная граница текущего MVP, а не импорт файлов произвольного размера с постоянным потреблением памяти.
Если лимиты будут повышены, потребуется отдельное дисковое/внешнее staging-хранилище до SQL-транзакции.
