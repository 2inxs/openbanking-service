# Граница сохранения

Операции PostgreSQL находятся в `TransactionRepository`, интерфейс — в `usecase/transaction`.
`Create` не строит ключ дедупликации сам: вызывающий сценарий передаёт устойчивую идентичность операции.
Ожидаемые дубли возвращают `transaction.ErrConflict`; ошибки ограничений данных не выдаются за успешный пропуск.
`List` ограничен владельцем и счётом, использует период `[from,to)` по `occurred_at` и порядок `(occurred_at DESC,id DESC)`.
Курсор репозитория — структурированная пара времени и UUID. Проверка/подпись HTTP-курсора остаётся delivery/usecase.

`persistence.TransactionRunner.Within` выдаёт набор репозиториев, использующих одну SQL-транзакцию.
В callback разрешены действия сохранения. Данные банка и файл читаются и валидируются ДО вызова `Within`.
Репозитории из callback нельзя сохранять для последующего использования или передавать другим горутинам.
Ошибка callback откатывает изменения, успешное завершение фиксирует их вместе.

Запись импорта создаётся `pending`, затем переводится в `processing` и `completed` либо `failed`.
Терминальные состояния не открываются повторно; повторная попытка после `failed` — новая запись.
Переход требует ожидаемый статус: устаревший писатель получает `statement.ErrImportConflict`.
Счётчики и безопасное сообщение ошибки фиксируются вместе с конечным статусом.

Если сама попытка была внутри откатившейся транзакции, её записи больше нет. После возврата ошибки
создайте отдельную запись `failed` через `ImportRecordRepository` вне откатившейся транзакции.
Не сохраняйте исходные ответы банка, токены или персональные данные в error_message.

Этот API — граница для сценариев импорта/синхронизации. Существующий потоковый импорт
`StatementImportRepository.ImportStream` пока управляет своей транзакцией отдельно и не переведён на `Within`.
Его дальнейшую интеграцию нужно согласовать с автором сценария: текущая реализация держит транзакцию
во время получения чанков. Не считать наличие нового TransactionRunner автоматическим исправлением этого пути.
